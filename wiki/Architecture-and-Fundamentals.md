## Technical Foundations

### 1. eBPF vs. Legacy Kernel Modules (LKM) — why it matters here
Traditional security agents compiled Loadable Kernel Modules against exact
kernel headers via DKMS. On a rolling release like Arch, kernel upgrades
routinely broke sensor compatibility.

Modern sensors instead use **eBPF** (`CONFIG_BPF=y`, `CONFIG_BPF_SYSCALL=y`),
which runs probes in kernel space, verified and sandboxed, decoupled from minor
kernel bumps. **That is a property of those sensors, not of Omarchy Sec.** This
project loads no eBPF programs of its own; `bin/omarchy-sec-detect` only
*reports* whether an eBPF runtime is active, by checking the `falco` and
`tetragon` systemd units.

### 2. Multi-Sensor Aggregation (`bin/omarchy-sec-detect`)
The detection engine checks systemd units (`systemctl is-active`), running
processes (`pgrep`), one marker file (`/opt/traps/bin/cytool`), and `docker ps`
for the Wazuh manager container. It emits JSON and nothing else — no network
calls, no log reads:
* Each sensor is reported as `active` or `inactive`. It does **not** query
  vendor health or engine versions; that granularity is not available from a
  unit-state check.
* Wazuh is reported as two independent fields, `agent` and `manager`. Reading
  `alerts.json` is the job of `omarchy-sec-wazuh-api` and `omarchy-sec-watcher`,
  not of the detector.
* `activeCount` counts Wazuh agent, Falcon, Cortex, SentinelOne, Defender and
  the eBPF runtime. **`auditd` is reported but deliberately not counted** — its
  presence alone is not endpoint protection.
* `status` is `protected` when `activeCount >= 1`, otherwise `unprotected`.

### 3. Wazuh REST API Client (`bin/omarchy-sec-wazuh-api`)
Authenticates against `https://localhost:55000/security/user/authenticate` and
caches the returned bearer token for 10 minutes in
`$XDG_RUNTIME_DIR/omarchy-sec/` (mode 0700, token file 0600). Credentials come
from environment variables or `~/.config/omarchy-sec/env`, generated by
`setup.sh`; there is no default password and the client exits `78` without one.
Subcommands:
* `summary`: agent list from `/agents` plus the last 5 alerts.
* `alerts [limit] [min_level]`: alerts read from `alerts.json` via `docker exec`,
  projected to level, rule ID, description, timestamp, source IP and file path.
  **No MITRE technique field is extracted.**
* `sca`: Security Configuration Assessment results from `/sca/<agent_id>`. Which
  policies apply depends on the policies Wazuh ships for the agent's OS.
* `fim`: file integrity changes from `/syscheck/<agent_id>`, covering whatever
  the agent's `syscheck` stanza monitors. The manager config in this repository
  watches `/etc`, `/usr/bin`, `/usr/sbin`, `/bin`, `/sbin` and `/boot` —
  **`~/.config/hypr` and the rest of `$HOME` are not monitored by default.**
* `query <endpoint>`: any REST endpoint, passed through.
